`@piplup/react-acl` holds the current user — the _principal_ — in a context and gates UI on their
roles and permissions. It gives you a `Can` component for markup, a `useAccessControl` hook for
checks in code, and the same checks as plain functions for everything outside React.

```package-install
@piplup/react-acl
```

## Quickstart

Wrap your app in `AccessControlProvider` and pass the principal. The provider fetches nothing — load
it however you like and pass the result in.

```tsx
import { AccessControlProvider, Can } from "@piplup/react-acl";

export default function App({ user }) {
  return (
    <AccessControlProvider principal={user}>
      <Can permission="invoice:write" fallback={<ReadOnlyNotice />}>
        <EditInvoice />
      </Can>
    </AccessControlProvider>
  );
}
```

A principal is just roles and permissions:

```ts
{ roles: ["admin"], permissions: ["invoice:read", "invoice:write"] }
```

Pass `undefined` while you are still fetching it. Every check then returns `false` and `Can` renders
its `loading` slot instead of its `fallback`, so nobody sees an access-denied state flash before the
data arrives. See [AccessControlProvider](/docs/react-acl/components/access-control-provider#loading).

<Callout type="warn">
  This hides UI. It does not protect data. Anything a user must not reach needs a check on your
  server as well.
</Callout>

## Upgrading from 3.x

Version 4 replaced the whole API: `AclProvider`, `HasAccess` and `useAcl` are gone, roles and
permissions moved into a single `principal`, permission lists now default to requiring **all** of
them rather than any, and permissions gained wildcards. The mapping is in the
[package's migration guide](https://github.com/piplupjs/piplup-react-acl#migrating-from-3x).
