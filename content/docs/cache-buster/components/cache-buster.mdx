`CacheBuster` checks once, when it mounts, whether a new build has been deployed since the user's last visit. Until the check finishes it renders `loading`; then it renders your app, or `error` if the check failed. It is a small wrapper around [`useReleaseStatus`](/docs/cache-buster/hooks/use-release-status).

Use `CacheBuster` when you want a gate around your app. Use `useReleaseStatus` when you want to act on the result yourself, for example to show an "update available" banner instead of reloading straight away.

## Basic usage

```tsx
import { CacheBuster } from "@piplup/cache-buster";

function App() {
  return (
    <CacheBuster
      enabled={process.env.NODE_ENV === "production"}
      loading={<SplashScreen />}
      error={<YourApp />}
    >
      <YourApp />
    </CacheBuster>
  );
}
```

The check needs a `RELEASE` file in your deployed site. Generate it at build time with the `piplup-cache-buster` CLI or the Vite plugin, as described in [Installation](/docs/cache-buster/installation).

## How the check works

1. On mount, it requests the release file, `/RELEASE` by default (see `url`), with `?v=<current timestamp>` added. The timestamp makes the URL unique, so the browser and CDN caches are skipped.
2. A response that isn't a 2xx status, or a body that looks like HTML (for example an SPA fallback `index.html`), counts as a failed check and the result is `error`. Otherwise the trimmed body is the release ID.
3. The release ID is compared with the value saved in `localStorage` under `storageKey` (default `"RELEASE"`). If they differ, the new ID is saved and the result is `new-release`.
4. If they match, the result is `no-release`.
5. If the request throws, for example when the user is offline, the result is `error`.

On a user's first visit nothing is stored yet. The ID is saved and the result is `no-release`, since the page was just loaded from the server and is already up to date.

The check runs once per page load for each `storageKey`, so React's StrictMode and several components using the same key share one request. There is no polling interval, so a tab that stays open will not notice a deployment until the page is reloaded. A failed check is not kept, so a `CacheBuster` that mounts later tries again.

## What it renders

| State | Renders | Default |
| --- | --- | --- |
| Check in progress | `loading` | nothing |
| `new-release` | `loading`, while the page reloads | nothing |
| `error` | `error` | nothing |
| `no-release` | `children` | nothing |
| `enabled={false}` | `children` after mount, without a request | — |

**Reloading.** On `new-release`, `CacheBuster` calls `window.location.reload()` and keeps rendering `loading`, so the old release does not flash on screen. The new ID is already saved, so the reloaded page reports `no-release`. A marker in `sessionStorage` allows one reload per release ID in each tab: if a server keeps returning a different ID, the second `new-release` renders `children` instead of reloading again.

During server rendering the check cannot run, so the server output is `loading`. The package is marked `"use client"`, so you can render `CacheBuster` from a Next.js layout.

If you want to decide yourself what happens on a new release, for example to show an "update available" banner instead of reloading, use [`useReleaseStatus`](/docs/cache-buster/hooks/use-release-status). The hook only reports the status and never reloads.

## Serving from a sub-path

The release file is requested from `/RELEASE` at the site root by default. If your app is served under a sub-path, pass its location as `url`. A relative URL resolves against the current page. With Vite, use the configured base:

```tsx
<CacheBuster url={`${import.meta.env.BASE_URL}RELEASE`}>
  <YourApp />
</CacheBuster>
```

`storageKey` only changes the `localStorage` key, not the URL. Give each app on the same origin its own `storageKey` so they don't overwrite each other's release ID.

## Gotchas

<Callout type="warn">
  `error` has no default, so if you wrap your app and the request fails, nothing renders. Pass your app (or a message) as `error` too, as in the example above.
</Callout>

- Set `verbose` to log each result to the console while you set things up.
